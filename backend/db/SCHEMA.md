# LeadRubyOrbit Database Schema

Phase 1 adds the Supabase PostgreSQL schema foundation for LeadRubyOrbit.

## Phase 1 Scope

- Initial PostgreSQL migration at `backend/db/migrations/001_initial_schema.sql`
- Core tables for teams, uploads, leads, campaigns, drafts, sent emails, replies, follow-ups, workflow settings, decisions, notifications, and audit logs
- Status check constraints for important workflow fields
- Foreign key relationships between workflow entities
- Useful lookup indexes
- Reusable `updated_at` trigger function
- Row level security enabled on public tables
- Backend configuration placeholders for Supabase and direct PostgreSQL connections

No application business logic is implemented in Phase 1.

## Tables

### team_members

Stores internal team member records. Roles are `admin`, `team_member`, and `viewer`. Status is `active` or `disabled`.

### lead_uploads

Stores metadata for uploaded lead files. Upload statuses are `uploaded`, `parsed`, `confirmed`, and `failed`. Phase 1 does not parse or import files.

### leads

Stores individual lead records and optional source upload references. Lead statuses are `new`, `imported`, `in_campaign`, `paused`, `stopped`, `replied`, and `no_reply`.

### campaigns

Stores campaign shells and optional future GHL workflow references. Campaign statuses are `draft`, `active`, `paused`, `completed`, and `archived`.

### campaign_leads

Joins campaigns to leads and tracks future sync/outreach state. Each lead can appear once per campaign. GHL sync statuses are `pending`, `synced`, and `failed`. Outreach statuses cover the later workflow from pending sync through approval, sending, reply handling, follow-up, pause, and stop states.

### email_accounts

Stores email account configuration placeholders. Account statuses are `enabled`, `disabled`, and `deleted`. Sensitive provider credentials should not be committed to source control.

### email_drafts

Stores draft email content and approval state. Draft types are `primary`, `followup`, `reply`, and `manual`. Draft statuses are `draft`, `saved`, `approved`, `rejected`, and `sent`.

### sent_emails

Stores sent email records and provider message/thread references. Statuses are `sent`, `failed`, `waiting_reply`, `replied`, and `no_reply`.

### replies

Stores detected reply records linked to sent emails, leads, campaigns, and campaign lead rows. Phase 1 does not implement reply checking.

### followups

Stores planned or completed follow-up records. Statuses are `draft`, `approved`, `sent`, `skipped`, and `stopped`.

### workflow_settings

Stores campaign-level timing settings for future reply checking and waiting periods. Supported time units are `seconds`, `minutes`, `hours`, and `days`.

### team_decisions

Stores manual decision tasks for the team. Reasons are `lead_replied`, `no_reply_timeout`, and `manual_review`. Statuses are `pending`, `resolved`, and `cancelled`. Actions include stopping outreach, creating follow-ups, drafting replies, manual email, moving stage, and manual handling.

### notifications

Stores team notification records. Priorities are `low`, `normal`, `high`, and `urgent`. Statuses are `unread` and `read`.

### audit_logs

Stores audit events with actor, action, entity, and metadata fields.

## Confirmed Business Rules

- IDs use UUIDs generated by `gen_random_uuid()` from `pgcrypto`.
- `campaign_leads` enforces one row per campaign and lead pair.
- `workflow_settings` enforces one settings row per campaign.
- Tables with `updated_at` use a shared trigger to refresh timestamps on update.
- Public tables have RLS enabled, but no access policies are created in Phase 1 because authentication and authorization rules are not implemented yet.
- Data API grants are intentionally not added yet. Supabase now supports projects where public tables are not exposed automatically, and app-specific access should be decided with the auth model in a later phase.

## Intentionally Not Implemented Yet

- Lead file upload, parsing, validation, or deduplication logic
- GHL integration or workflow syncing
- AI-generated email content
- Email sending or provider integrations
- Reply checking workers
- Follow-up scheduling workers
- Notifications delivery
- Authentication and authorization policies
- Frontend pages backed by real database data
